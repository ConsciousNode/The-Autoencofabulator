# AUDIT-2: v0.4.0 "Learned"

*Kehai Interim, 2026-11-05. Audit of Argon's v0.4.0 delivery (commit `70641e2`).*

The usage budget was tight this week, so the audit was deliberately uneven: one deep dive where test-set leakage could hide, light checks everywhere else. Every number below was produced on this machine from the committed code.

## Verdict

**The headline Sherlock result is real and it reproduces.** No test-set peeking was found. The constants Argon hand-set are *under*-tuned rather than leaked: a val-only search beats them on test. The generation-side "no copying" claim also holds up, once you compare against the right floor.

There are three honest caveats about what the result *means*. They're in the next section, and README/REALIZED-2 should carry them.

## 2. Deep dive: were the joining constants picked on test?

The design: during training the transformer runs with the memory disabled (`disableMemory: true` on every batch), and `tfScale` and `ctxGate` are frozen (`lrScale = 0`). The two are joined *after* training as a log-linear mixture:

`comb = mixScale·tfLogits + gate·memLogP`, where `mixScale = 0.56` is hard-coded and α / gate are picked from three hand-written candidates on val.

The test split is touched exactly once in the script. But hand-written constants could have been tuned across *earlier* runs while someone watched test. So I swept them with the shipped checkpoint, scoring **all 878 val and all 878 test windows** (`tests/audit-v04-sweep.js`).

**mixScale** (α 0.53, gate 0.60 as shipped):

| mixScale | 0.40 | 0.44 | 0.48 | **0.52** | *0.56 (shipped)* | 0.60 | 0.64 | 0.72 | 1.00 |
|---|---|---|---|---|---|---|---|---|---|
| val | 2.8451 | 2.8381 | 2.8341 | **2.8328** | 2.8341 | 2.8377 | 2.8436 | 2.8616 | 2.9771 |
| test | 2.8982 | 2.8932 | **2.8911** | 2.8918 | 2.8951 | 2.9007 | 2.9086 | 2.9306 | 3.0609 |

**α × gate** grid (mixScale 0.56): the val optimum is α 0.60 / gate 0.45 (val 2.8283), which gives **test 2.8862**. The test optimum in the grid is α 0.55 / gate 0.45 (test 2.8853). The shipped α 0.53 / gate 0.60 gives test 2.8951.

**Reading:** the shipped constants are not optimal on test, so they weren't fitted to it. Val and test optima sit close together, so val is a faithful proxy. A plain val-only grid search would have *improved* the reported test number by about 0.009 bpb. This is clean.

## 3. Caveats on what the result means

1. **Tier 1's "the gate receives gradients" is not met as specified.** The gate is frozen during training and calibrated afterwards on val. That's a defensible design (product of experts with val-calibrated temperatures), but REALIZED-2 should say "post-hoc calibrated", not "learned".
2. **The joint only works when damped.** With `mixScale = 1.0` (no damping) the full model scores test 3.0609, worse than either component alone. The gain comes from treating the two as calibrated experts, not from a model that learned to use its memory. That is the obvious next research step: train with the memory in the loop.
3. **"Transformer alone" carries a learned hashed-context table.** `_contextBuckets` hashes the ±3 neighbours into 6 tables (`ctxEmb`), which are input features added to the token embedding. I checked that this isn't a leak: the hashes read only `tokens[i±k]`, never `tokens[i]`, and masked neighbours hash as MASK. But it does mean much of the 1.23 M parameters is an n-gram-style lookup rather than attention. Fair to call it a transformer; worth saying so plainly.
4. **The comparison to Kneser-Ney needs its caveat kept.** Causal KN4 gets 2.3222 on test, well below 2.8951. That's not apples to apples: masked bpb averaged over t ∈ 0.1…0.9 isn't the causal next-byte bpb. REALIZED-2 already labels KN4 as a "causal reference", and that label should stay next to the number. The comparable baseline is the bilateral count memory (3.0265), and the full model beats it by 0.131 bpb.

## 5. LCS memorisation: compared against its floor

A raw LCS ratio means nothing without knowing how much two *genuinely different* documents from the same generator overlap. `tests/audit-v04-lcs.js` scores the held-out generator documents (seed 97531, the real data, not model output) against the training suite (seed 4242), at the sizes `metrics.js` uses.

| Format | Fresh held-out doc vs train (mean / max) | Model output, REALIZED-2 (range over regimes) |
|---|---|---|
| HTML | 0.610 / 0.749 | 0.501–0.576 |
| JSON | 0.441 / 0.459 | 0.452–0.517 |
| SVG | 0.731 / 0.763 | 0.717–0.762 |
| JS | 0.481 / 0.551 | 0.527–0.562 |
| C | 0.615 / **1.000** | 0.574–0.752 |
| BMP | **1.000** / 1.000 | 0.985 |

**Reading:** model output overlaps training about as much as a fresh real document does, which is what "not copying" should look like. C from-scratch (0.752) runs somewhat above the floor and is the one to watch.

Two problems with the metric itself:

- **BMP LCS is uninformative.** `longestCommonSubstringRatio` only examines the first 512 bytes of the sample (and 1024 of each reference). For a 32×32 BMP those are the header plus a few rows of background, which are the same in every image, so every BMP scores ~1.0. A future version should compare pixel data past the header, or the whole file.
- **One "held-out" C document is a byte-identical copy of a training document** (1 of 10; checked by SHA-1). The C generator has low diversity at these seeds. This slightly inflates C held-out repair/validity. `metrics.js` should de-duplicate held-out docs against training before evaluating. Not changed here, to avoid a re-run this week; the numbers in REALIZED-2 include that document.

The UI's novelty threshold (`lcsRatio < 0.65` → "novel ✓") is also below the real-data floor for SVG and BMP, so genuine fresh SVGs would read as "high overlap". A per-format floor would be more honest.

## Suggested for v0.5

1. Train with the memory in the loop, and let the gate learn; report the gain over post-hoc calibration.
2. Replace the three hand-written candidates and `mixScale = 0.56` with a val grid search (or learn them).
3. De-duplicate held-out docs against training in `metrics.js`; make LCS cover the whole file (or the post-header payload); use per-format novelty floors.
4. Report the hashed-context table's share of the parameters, and the "transformer alone" score with `ctxEmb` ablated.
